# chibipop M3 — Popup Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A layered popup beside the hovered character showing its definition, driven by low-level input hooks, without stealing focus and without appearing in chibipop's own screen captures.

**Architecture:** A pure `present.rs` turns the engine's ranked `Hit`s into a `Presentation` (merged cards, dictionary order, collapsed rows) with no Windows dependency. A Win32 main thread owns the message loop, the hooks, the popup window and the tray; one worker thread runs capture → OCR → lookup → present. Staleness is resolved by a monotonic `RequestId`.

**Tech Stack:** Rust 2021, `windows` 0.62.2 (eleven features), `toml`, on top of the existing `rusqlite`/`serde`/`serde_json`/`anyhow`/`clap`/`windows-future`.

## Verified API facts — do not re-derive, do not "correct"

Two throwaway spikes compiled and ran against this machine before this plan was written. Both are vendored in the repo:

- `docs/superpowers/findings/2026-07-27-m3-win32-d2d-spike.md` — layered window, D2D/DirectWrite, capture exclusion, hooks, tray. **Read it before Tasks 1, 5, 6 and 8; it contains working code.**
- `docs/superpowers/findings/2026-07-26-m2-winrt-ocr-spike.md` — the WinRT/OCR surface from M2.

Load-bearing facts:

1. **`WDA_EXCLUDEFROMCAPTURE` is incompatible with per-pixel alpha.** On an `UpdateLayeredWindow` popup it fails with `HRESULT(0x80070008)` — "not enough memory", which is a lie — and **silently no-ops**, leaving 91% of the popup's pixels in a BitBlt. With `SetLayeredWindowAttributes(LWA_ALPHA)` and `WM_PAINT` it succeeds: **0 of 76,800 pixels captured**. A non-layered control also excludes cleanly, isolating `UpdateLayeredWindow` as the trigger.
2. Therefore the popup is `WS_EX_LAYERED` + `SetLayeredWindowAttributes(LWA_ALPHA)`, painted via **`ID2D1HwndRenderTarget` on `WM_PAINT`**, with `SetWindowRgn(CreateRoundRectRgn(...))` for a rounded (hard-edged) silhouette.
3. **`WS_EX_NOACTIVATE` alone prevents focus theft** — verified across `SW_SHOW`, `SW_SHOWNOACTIVATE` and `SetWindowPos`+`SWP_NOACTIVATE`.
4. **`HOOKPROC` is a bare `extern "system" fn` and cannot capture.** State must reach it through statics/atomics. Hooks only fire while the owning thread pumps messages.
5. **Win32 features carry the `Win32_` prefix; WinRT ones do not.** The eleven needed here: `Win32_Foundation`, `Win32_UI_WindowsAndMessaging`, `Win32_UI_HiDpi`, `Win32_UI_Input_KeyboardAndMouse`, `Win32_UI_Shell`, `Win32_Graphics_Gdi`, `Win32_Graphics_Direct2D`, `Win32_Graphics_Direct2D_Common`, `Win32_Graphics_Dxgi_Common`, `Win32_Graphics_DirectWrite`, `Win32_System_LibraryLoader`. `Win32_Graphics_Dxgi_Common` is needed for exactly one constant (`DXGI_FORMAT_B8G8R8A8_UNORM`) and is easy to miss.
6. **No COM initialisation is required** for the D2D/DirectWrite path.

## Task 2: The presentation model

**Files:** Create `src/present.rs`; modify `src/lib.rs`, `src/lookup/model.rs`, `src/lookup/sqlite.rs`

**Interfaces:**
- Consumes: `Hit`, `Entry`, `Sense` from `lookup::model`
- Produces: `Presentation`, `Card`, `GlossBlock`, `CollapsedRow`, `DictInfo`, `PresentConfig`, `pub fn build(hits: &[Hit], dicts: &[DictInfo], cfg: &PresentConfig) -> Presentation`; and `Dictionary::dicts(&self) -> Result<Vec<DictInfo>>` on the trait, `SqliteDictionary` and `FakeDictionary`

This is the part of M3 most likely to be wrong and the only part fully testable. **No `windows` dependency.**

Rules from spec §4.1:
- Group hits by `(written, reading)`. A group's position is the rank of its **best** hit, so merging never reorders groups relative to each other.
- First group → `top`; every other group → a `CollapsedRow`.
- Within a card, blocks are ordered by `cfg.dict_order` — a list of **case-insensitive substrings** matched against the dictionary name. Unmatched dictionaries sort last, by `dict_id`. Substrings rather than exact names because Jitendex's name embeds a release date that changes on update.
- `CollapsedRow::summary` is the first gloss of the first block, cut to `cfg.summary_chars` **characters, not bytes**, with `…` appended **only when it actually cut**.
- A hit whose `dict_id` matches no `DictInfo` still produces a block (named by its id), rather than being dropped.

## Task 6: Low-level input hooks

**Files:** Create `src/input/mod.rs`, `src/input/hooks.rs`; modify `src/lib.rs`

**Interfaces:**
- Produces: `pub struct Hooks` with `pub fn install() -> Result<Hooks>` and `Drop` that unhooks; `pub fn set_mode(m: TriggerMode)`; `pub fn take_pending() -> Option<PhysPoint>`

**Read the spike findings' hook section first.** Verified fact 4: `HOOKPROC` is a bare `extern "system" fn` that **cannot capture**, so state reaches it through statics. Hooks only fire while the owning thread pumps messages.

Requirements:

- `WH_MOUSE_LL` records the cursor position on `WM_MOUSEMOVE`; `WH_KEYBOARD_LL` tracks Shift down/up.
- In `Live` mode every move is a candidate; in `HoldShift` only moves while Shift is down.
- **The 4-pixel movement gate lives here or in `app.rs`, not in a poll loop** — the hook fires on every mouse event, and re-resolving on a one-pixel tremor would be far worse than it was at M2's 8 Hz.
- **`catch_unwind` inside both callbacks.** Unwinding across a Win32 callback boundary is undefined behaviour — this is not optional.
- Both hooks must call `CallNextHookEx` so other applications keep working. A low-level hook that swallows input makes the machine unusable.
- `Drop` calls `UnhookWindowsHookEx` for both.
- `install()` returns `Err` if either hook fails; per spec §6 the caller treats that as a **hard
  failure at startup**, naming which hook — without hooks there is no product.

```bash
cargo build
```

**Files:** Create `src/app.rs`; modify `src/main.rs`, `src/lib.rs`

**Interfaces:**
- Consumes: everything from Tasks 1–6, plus M2's `OcrTextSource` and M1's `LookupEngine`/`SqliteDictionary`
- Produces: `pub fn run(cfg: Config) -> Result<()>`, and a `run` subcommand on the CLI

This is the milestone's integration point: the two-thread architecture from spec §4.

Requirements:

- Main thread: create the popup, install the hooks, create the tray (Task 8 adds the menu; wire the icon here), pump messages.
- One worker thread: receives `Trigger { cursor, id }` from a single-slot channel, runs `OcrTextSource::resolve_at` → `LookupEngine::run` → `present::build`, and posts `WM_APP_RESULT` with the id.
- **Staleness by `RequestId` comparison, not sentinel values.** Drop a result whose id is older than the latest dispatched.
- On a result: `measure`, `place_popup` against the monitor containing the anchor, `show_at`, paint. On `None`: hide.
- `dicts()` is called **once** at startup and the `Vec<DictInfo>` reused.
- Shutdown: clear the run flag, drop the sender, drop `Hooks`, `PostQuitMessage`.
- **`SetProcessDpiAwarenessContext` before any GDI call**, and report `capture_excluded()` at startup — a `false` there must be printed loudly, since it means every hover will photograph the popup.

## Task 10: Make the popup recordable on request

**Files:** Modify `src/config.rs`, `src/ui/window.rs`, `src/app.rs`

**Interfaces:**
- Consumes: `Config`, `Popup`
- Produces: `[popup] exclude_from_capture` (default `true`); `Popup::create(exclude: bool)`; a hide-and-reshow guard around each capture when exclusion is off

**Execute this after Task 8 and before Task 9**, so Task 9's memory readings are taken against the
final code.

Discovered in use: capture exclusion hides the popup from **every** capture API, so the user cannot
screen-record, screenshot, or screen-share it. See spec §5.1.

- [ ] **Step 1: Add the config key**

`exclude_from_capture: bool` in the `[popup]` section, **defaulting to `true`**. Add a test asserting
the default, alongside the existing `defaults_match_the_spec`.

- [ ] **Step 2: Make exclusion conditional**

`Popup::create` takes the flag. When `false`, skip `SetWindowDisplayAffinity` entirely — do not call
it and ignore the result, since a stored `capture_excluded()` of `false` must mean "deliberately off",
not "tried and failed". Distinguish the two in what is reported at startup.

- [ ] **Step 3: Guard the capture**

In `app.rs`, when exclusion is off, hide the popup immediately before each capture and reshow it after,
so it never appears in its own OCR input. **Do not skip this guard.** Without it the popup's text lands
in the captured region and can be caught by the hit-scan's near-miss tolerance — occasional silent
wrong answers, which is worse than a visible flicker.

- [ ] **Step 4: Verify both modes**

With the default (`true`): confirm the popup still does not appear in a screen capture. With `false`:
confirm it **does** appear in a capture, and that hovering still resolves the correct character rather
