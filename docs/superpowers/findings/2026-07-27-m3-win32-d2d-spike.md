## 1. Cargo.toml (verified-minimal feature list)

Every feature below was empirically required. `Win32_System_Com` and `Win32_System_Threading` were in my first draft (carried over from assumptions, never actually called anything from them) and were removed after confirming the crate still builds without them. `Win32_Graphics_Dxgi_Common` and `Win32_UI_HiDpi` were spot-checked by deleting each individually and recompiling — both fail immediately without their feature (errors below). The rest are exercised directly by symbols visibly imported and used in `main.rs`, which is a mechanical/compile-time guarantee in windows-rs (a glob-import of a Win32 submodule cannot resolve without its feature flag), not a guess.

```rust
#![allow(non_snake_case)]

// ---- globals used by the LL hook callbacks (extern "system" fn pointers can't capture) ----
static MOUSE_EVENTS: AtomicU32 = AtomicU32::new(0);
static KEY_EVENTS: AtomicU32 = AtomicU32::new(0);
static LAST_MOUSE_X: AtomicI32 = AtomicI32::new(0);
static LAST_MOUSE_Y: AtomicI32 = AtomicI32::new(0);
static SHIFT_DOWN: AtomicBool = AtomicBool::new(false);

const POPUP_W: i32 = 480;
const POPUP_H: i32 = 160;
// secondary monitor spans x 2560..3639 (1080 wide), y 0..1920 (portrait)
const POPUP_X: i32 = 2700;
const POPUP_Y: i32 = 300;

// dark rounded panel fill color (straight RGB, 0..255)
const PANEL_R: u8 = 26;
const PANEL_G: u8 = 24;
const PANEL_B: u8 = 38;

fn wide(s: &str) -> Vec<u16> {
    s.encode_utf16().collect()
}

fn rgb(r: u8, g: u8, b: u8) -> u32 {
    (r as u32) | ((g as u32) << 8) | ((b as u32) << 16)
}

unsafe extern "system" fn wndproc(hwnd: HWND, msg: u32, wparam: WPARAM, lparam: LPARAM) -> LRESULT {
    match msg {
        WM_DESTROY => {
            PostQuitMessage(0);
            LRESULT(0)
        }
        WM_PAINT => {
            // Only used by the V2/V3 display-affinity control windows, which paint a plain
            // solid rect via GDI instead of going through UpdateLayeredWindow.
            let mut ps = PAINTSTRUCT::default();
            let hdc = BeginPaint(hwnd, &mut ps);
            let mut rc = RECT::default();
            let _ = GetClientRect(hwnd, &mut rc);
            let brush = CreateSolidBrush(COLORREF(rgb(PANEL_R, PANEL_G, PANEL_B)));
            FillRect(hdc, &rc, brush);
            let _ = DeleteObject(brush.into());
            let _ = EndPaint(hwnd, &ps);
            LRESULT(0)
        }
        _ => DefWindowProcW(hwnd, msg, wparam, lparam),
    }
}

unsafe extern "system" fn mouse_hook_proc(code: i32, wparam: WPARAM, lparam: LPARAM) -> LRESULT {
    if code >= 0 {
        let data = &*(lparam.0 as *const MSLLHOOKSTRUCT);
        LAST_MOUSE_X.store(data.pt.x, Ordering::Relaxed);
        LAST_MOUSE_Y.store(data.pt.y, Ordering::Relaxed);
        let n = MOUSE_EVENTS.fetch_add(1, Ordering::Relaxed);
        if n < 6 {
            println!("[mouse-hook] #{n} pt=({}, {}) wparam={}", data.pt.x, data.pt.y, wparam.0);
        }
    }
    CallNextHookEx(None, code, wparam, lparam)
}

unsafe extern "system" fn keyboard_hook_proc(code: i32, wparam: WPARAM, lparam: LPARAM) -> LRESULT {
    if code >= 0 {
        let data = &*(lparam.0 as *const KBDLLHOOKSTRUCT);
        let shift = (GetAsyncKeyState(VK_SHIFT.0 as i32) as u16 & 0x8000) != 0;
        SHIFT_DOWN.store(shift, Ordering::Relaxed);
        let n = KEY_EVENTS.fetch_add(1, Ordering::Relaxed);
        if n < 6 {
            println!("[kb-hook] #{n} vk={} shift={} wparam={}", data.vkCode, shift, wparam.0);
        }
    }
    CallNextHookEx(None, code, wparam, lparam)
}

/// BitBlt the given screen rect into a 32bpp top-down DIB and return the raw pixel bytes (BGRA/BGRX).
unsafe fn capture_region(x: i32, y: i32, w: i32, h: i32) -> Vec<u8> {
    let screen_dc = GetDC(None);
    let cap_dc = CreateCompatibleDC(Some(screen_dc));
    let bmp = CreateCompatibleBitmap(screen_dc, w, h);
    let old = SelectObject(cap_dc, bmp.into());
    let _ = BitBlt(cap_dc, 0, 0, w, h, Some(screen_dc), x, y, SRCCOPY);

    let mut bmi = BITMAPINFO::default();
    bmi.bmiHeader.biSize = size_of::<BITMAPINFOHEADER>() as u32;
    bmi.bmiHeader.biWidth = w;
    bmi.bmiHeader.biHeight = -h; // top-down
    bmi.bmiHeader.biPlanes = 1;
    bmi.bmiHeader.biBitCount = 32;
    bmi.bmiHeader.biCompression = BI_RGB.0 as u32;

    let mut buf = vec![0u8; (w * h * 4) as usize];
    GetDIBits(
        cap_dc,
        bmp,
        0,
        h as u32,
        Some(buf.as_mut_ptr() as *mut c_void),
        &mut bmi,
        DIB_RGB_COLORS,
    );

    SelectObject(cap_dc, old);
    let _ = DeleteObject(bmp.into());
    let _ = DeleteDC(cap_dc);
    ReleaseDC(None, screen_dc);
    buf
}

/// Count pixels in a captured BGRX buffer that match the popup panel's known fill color.
fn count_panel_pixels(buf: &[u8]) -> usize {
    let mut count = 0usize;
    for chunk in buf.chunks_exact(4) {
        let b = chunk[0] as i32;
        let g = chunk[1] as i32;
        let r = chunk[2] as i32;
        if (r - PANEL_R as i32).abs() < 12 && (g - PANEL_G as i32).abs() < 12 && (b - PANEL_B as i32).abs() < 12 {
            count += 1;
        }
    }
    count
}

/// Create a short-lived window with the given ex-style, optionally set constant-alpha via
/// SetLayeredWindowAttributes (the OTHER layered-window flavor, as opposed to UpdateLayeredWindow),
/// then try WDA_EXCLUDEFROMCAPTURE on it and report whether it succeeded and whether capture
/// actually excludes it. Used to isolate which window property triggers the display-affinity bug.
unsafe fn test_variant(
    hinstance: HINSTANCE,
    class_name: PCWSTR,
    label: &str,
    ex_style: WINDOW_EX_STYLE,
    use_layered_attrs: bool,
    round_region: bool,
    x: i32,
    y: i32,
) {
    println!("--- variant [{label}] ex_style=0x{:X} ---", ex_style.0);
    let hwnd = match CreateWindowExW(
        ex_style,
        class_name,
        w!("M3Spike Variant"),
        WS_POPUP,
        x,
        y,
        POPUP_W,
        POPUP_H,
        None,
        None,
        Some(hinstance),
        None,
    ) {
        Ok(h) => h,
        Err(e) => {
            println!("[{label}] CreateWindowExW FAILED: {e:?}");
            return;
        }
    };

    if use_layered_attrs {
        match SetLayeredWindowAttributes(hwnd, COLORREF(0), 230, LWA_ALPHA) {
            Ok(()) => println!("[{label}] SetLayeredWindowAttributes(LWA_ALPHA=230) ok"),
            Err(e) => println!("[{label}] SetLayeredWindowAttributes FAILED: {e:?}"),
        }
    }

    if round_region {
        let rgn = CreateRoundRectRgn(0, 0, POPUP_W, POPUP_H, 28, 28);
        let set_ok = SetWindowRgn(hwnd, Some(rgn), true);
        println!("[{label}] SetWindowRgn(rounded 28x28) result={set_ok}");
    }

    let _ = SetWindowPos(
        hwnd,
        Some(HWND_TOPMOST),
        x,
        y,
        POPUP_W,
        POPUP_H,
        SWP_NOACTIVATE | SWP_SHOWWINDOW,
    );
    std::thread::sleep(Duration::from_millis(250));

    let affinity_result = SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE);
    println!("[{label}] SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE) => {:?}", affinity_result);

    std::thread::sleep(Duration::from_millis(250));
    let cap = capture_region(x, y, POPUP_W, POPUP_H);
    let hits = count_panel_pixels(&cap);
    println!(
        "[{label}] captured panel-colored pixels AFTER affinity attempt = {hits} / {} ({}% )",
        POPUP_W * POPUP_H,
        hits * 100 / (POPUP_W * POPUP_H) as usize
    );

    let _ = DestroyWindow(hwnd);
    std::thread::sleep(Duration::from_millis(100));
}

        let dib = CreateDIBSection(Some(screen_dc), &bmi, DIB_RGB_COLORS, &mut bits, None, 0)?;
        let mem_dc = CreateCompatibleDC(Some(screen_dc));
        let old_bmp = SelectObject(mem_dc, dib.into());

        let rt_props = D2D1_RENDER_TARGET_PROPERTIES {

        let bind_rect = RECT { left: 0, top: 0, right: POPUP_W, bottom: POPUP_H };

        dc_rt.Clear(Some(&D2D1_COLOR_F { r: 0.0, g: 0.0, b: 0.0, a: 0.0 }));

        let mut win_pt = POINT { x: POPUP_X, y: POPUP_Y };
        let blend = BLENDFUNCTION {

        UpdateLayeredWindow(

            false,
            false,

            hinstance,

            true,

        let mouse_hook = SetWindowsHookExW(WH_MOUSE_LL, Some(mouse_hook_proc), Some(hinstance), 0)?;
        let kb_hook = SetWindowsHookExW(WH_KEYBOARD_LL, Some(keyboard_hook_proc), Some(hinstance), 0)?;
        println!("mouse_hook={:?} kb_hook={:?}", mouse_hook, kb_hook);
        println!("pumping messages for 6s, logging up to 6 real events per hook (no synthetic input injected)...");

        let start = Instant::now();
        let mut msg = MSG::default();
        while start.elapsed() < Duration::from_secs(6) {
            while PeekMessageW(&mut msg, None, 0, 0, PM_REMOVE).as_bool() {
                let _ = TranslateMessage(&msg);
                DispatchMessageW(&msg);
            }
            std::thread::sleep(Duration::from_millis(15));
        }
        println!(
            "hook totals: mouse_events={} key_events={} last_mouse=({}, {}) shift_down_last_seen={}",
            MOUSE_EVENTS.load(Ordering::Relaxed),
            KEY_EVENTS.load(Ordering::Relaxed),
            LAST_MOUSE_X.load(Ordering::Relaxed),
            LAST_MOUSE_Y.load(Ordering::Relaxed),
            SHIFT_DOWN.load(Ordering::Relaxed)
        );

        let unhook_mouse_ok = UnhookWindowsHookEx(mouse_hook);
        let unhook_kb_ok = UnhookWindowsHookEx(kb_hook);
        println!("unhook results: mouse={:?} kb={:?}", unhook_mouse_ok, unhook_kb_ok);

        // ---- cleanup ----
        println!("=== cleanup ===");
        let tray_removed = Shell_NotifyIconW(NIM_DELETE, &nid);
        println!("Shell_NotifyIconW(NIM_DELETE) = {:?}", tray_removed.as_bool());
        SelectObject(mem_dc, old_bmp);
        let _ = DeleteObject(dib.into());
        let _ = DeleteDC(mem_dc);
        ReleaseDC(None, screen_dc);
        let _ = DestroyWindow(hwnd);
        let _ = UnregisterClassW(class_name, Some(hinstance));

        println!("=== done ===");
        Ok(())
    }
}

fn main() {
    if let Err(e) = run() {
        eprintln!("FATAL: {e:?}");
        std::process::exit(1);
    }
}
```

## 3. Capture-exclusion verdict — THE key result

**Short answer: it depends entirely on how the popup renders its transparency, and this is a hard OS-level split, not a tuning knob.**

- **`WS_EX_LAYERED` window painted via `UpdateLayeredWindow` (true per-pixel alpha — the approach goal 2 asked for and that I built first): `SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` FAILS**, every single run (3/3), with:
  ```
  Error { code: HRESULT(0x80070008), message: "Not enough memory resources are available to process this command." }
  ```
  That HRESULT is `HRESULT_FROM_WIN32(ERROR_NOT_ENOUGH_MEMORY)` — and per multiple corroborating sources (see below) it is a **known-misleading error string**; the real cause is unrelated to memory. Confirmed this is not a fluke of my capture method: **Test A** (before attempting the affinity call) BitBlt'd the popup's screen rect and found **69908/76800 pixels (91%)** matching the panel's exact fill color — proof the window really is visible and my capture method really does pick it up. **Test B** (immediately after the failed affinity call) captured the identical **69908/76800 (91%)** — i.e. nothing changed, because the call never took effect.

- **The same window shape/position/topmost/no-activate flags, but `WS_EX_LAYERED` painted via `SetLayeredWindowAttributes(hwnd, 0, 230, LWA_ALPHA)` (constant/uniform alpha, driven by ordinary `WM_PAINT` + GDI, not `UpdateLayeredWindow`): `SetWindowDisplayAffinity` SUCCEEDS (`Ok(())`), and the post-affinity BitBlt of that window's rect found **0/76800 (0%)** panel-colored pixels** — full exclusion, confirmed by direct measurement, not just "the call didn't error."

- **Control: a plain non-layered window** (same `WS_EX_NOACTIVATE | WS_EX_TOPMOST | WS_EX_TOOLWINDOW`, no `WS_EX_LAYERED` at all, opaque `WM_PAINT` fill): `SetWindowDisplayAffinity` also SUCCEEDS, **0/76800 (0%)** captured. This isolates that `WS_EX_LAYERED`-with-`UpdateLayeredWindow` specifically is the trigger — not `WS_EX_TOPMOST`/`WS_EX_NOACTIVATE`/`WS_EX_TOOLWINDOW`, and not "layered" in general.

- **The practical workaround, tested end to end**: `WS_EX_LAYERED` + `SetLayeredWindowAttributes(LWA_ALPHA)` **plus** `SetWindowRgn(hwnd, CreateRoundRectRgn(0,0,w,h,28,28), true)` for a rounded silhouette: `SetWindowRgn` succeeds (`result=1`), `SetWindowDisplayAffinity` succeeds (`Ok(())`), and capture shows **0/76800 (0%)**. So you *can* keep a rounded panel shape and get capture exclusion — you just can't have smooth per-pixel-AA rounded corners; the region-clipped corners are hard/aliased pixel cuts, not anti-aliased.

Raw log excerpt from the final verified run (identical across all 3 runs of the day):
```

Test B -- after WDA_EXCLUDEFROMCAPTURE attempt: panel-colored pixels captured = 69908 / 76800 (91%)
```

**Corroborating external evidence** (this is a documented, widely-hit issue, not specific to this machine — it affects Chrome, Edge, Firefox, Teams on Windows 11 too, per a Microsoft Q&A thread):
- [SetWindowDisplayAffinity on windows 11 - Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/700122/setwindowdisplayaffinity-on-windows-11) — reports of `ERROR_NOT_ENOUGH_MEMORY (0x8)` from `SetWindowDisplayAffinity` tied to `WS_EX_LAYERED`, affecting real shipped apps; the only Microsoft-side mitigation offered is an application-compatibility shim (`LegacyDisplayAffinity` via a custom `.sdb`, installed per-machine with `sdbinst.exe`) — not viable for a distributed app. Root cause traced by the community to `ChangeWindowTreeProtection()` in `win32kfull.sys`.
- [SetWindowDisplayAffinity bad usecase - Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/1653885/setwindowdisplayaffinity-bad-usecase) — separate discussion of `WDA_EXCLUDEFROMCAPTURE`/`WDA_NONE` semantics.
- General search corroboration: layered windows are documented to come in two mutually exclusive flavors — `SetLayeredWindowAttributes`-driven (color-key or constant alpha) vs `UpdateLayeredWindow`-driven (per-pixel alpha, what WPF's `AllowsTransparency="True"` uses under the hood) — and community reports specifically say Windows does not support display-affinity exclusion for the `UpdateLayeredWindow` flavor. My own controlled A/B/control test above is the strongest evidence though, since it isolates the variable directly on this exact machine/driver/OS build rather than relying on secondhand reports.

**Bottom line for the plan**: you cannot have both true per-pixel-alpha rendering (`UpdateLayeredWindow`) *and* `WDA_EXCLUDEFROMCAPTURE` on the same window. For chibipop's requirement ("must not appear in the app's own BitBlt capture" is explicitly the critical one), the popup **must** be built as `WS_EX_LAYERED` + `SetLayeredWindowAttributes(LWA_ALPHA)` (uniform translucency) with normal GDI/D2D-via-`ID2D1HwndRenderTarget` painting driven by `WM_PAINT`, optionally combined with `SetWindowRgn` for a rounded (hard-edged) silhouette — not the DC-render-target-plus-`UpdateLayeredWindow` approach, even though the latter looks nicer (smooth AA rounded corners, true variable per-pixel alpha for soft shadows etc.). This is a real, load-bearing visual-quality tradeoff that a plan needs to bake in up front, not discover after the rendering code is written.

I did not have time in this spike to test whether `ID2D1HwndRenderTarget` (rendering straight into the `WS_EX_LAYERED`+`LWA_ALPHA` window's own DC via `WM_PAINT`, rather than the GDI `FillRect` stand-in I used for V2/V4) also passes `WDA_EXCLUDEFROMCAPTURE` — I'd bet yes (the window's fundamental style/paint-model class is unchanged, only what's drawn into it differs), but that's an inference, not something I measured. Worth a 15-minute follow-up before committing to it in the real app.

## 4. D2D surface creation and painting (goal 2 detail)

**Render-target flavour used: `ID2D1DCRenderTarget` (a DC render target), not `ID2D1HwndRenderTarget`.** This was a deliberate choice, not just "what compiled first": `ID2D1HwndRenderTarget` paints directly into a normal HWND's own device context in response to `WM_PAINT`/`WM_ERASEBKGND` — it has no mechanism to hand DWM a bitmap with an alpha channel that gets composited transparently against the desktop. Per-pixel alpha on a layered window is achieved a different way entirely: you render into an off-screen 32bpp premultiplied-alpha DIB section, then call `UpdateLayeredWindow` to hand that bitmap (plus a memory DC) to the window manager as the window's entire visual content. `ID2D1DCRenderTarget` is the D2D object designed to bind to exactly that kind of memory DC (`BindDC`), so it was the correct/only choice for combining D2D with `UpdateLayeredWindow`.

Concretely, in dependency order:
1. `SetProcessDpiAwarenessContext(DPI_AWARENESS_CONTEXT_PER_MONITOR_AWARE_V2)` — first call in the program, before any window or GDI/D2D call.
2. Register window class + `CreateWindowExW` (window created, but not yet shown/painted — no `WS_VISIBLE`).
3. `D2D1CreateFactory::<ID2D1Factory>(D2D1_FACTORY_TYPE_SINGLE_THREADED, None)` and `DWriteCreateFactory::<IDWriteFactory>(DWRITE_FACTORY_TYPE_SHARED)`.
4. `GetDC(None)` for the screen DC, `CreateDIBSection` (32bpp, top-down, `biHeight` negative) bound into a `CreateCompatibleDC` memory DC via `SelectObject`.
5. `d2d_factory.CreateDCRenderTarget(&D2D1_RENDER_TARGET_PROPERTIES{ pixelFormat: { format: DXGI_FORMAT_B8G8R8A8_UNORM, alphaMode: D2D1_ALPHA_MODE_PREMULTIPLIED }, .. })`, then `dc_rt.BindDC(mem_dc, &rect)`.
6. `BeginDraw()` → `Clear(D2D1_COLOR_F{ a: 0.0, .. })` (fully transparent) → `FillRoundedRectangle` for the dark panel (brush alpha 0.92) → `CreateTextFormat("Yu Gothic UI", .., 19.0, "ja-JP")` → `DrawText` with a `&[u16]` (no `w!` macro here since the string needs to combine Japanese + English + `\r\n`, built via `.encode_utf16().collect()`) → `EndDraw()`.
7. `UpdateLayeredWindow(hwnd, screen_dc, &window_pos, &size, mem_dc, &src_pt, COLORREF(0), &BLENDFUNCTION{ BlendOp: AC_SRC_OVER, SourceConstantAlpha: 255, AlphaFormat: AC_SRC_ALPHA }, ULW_ALPHA)` — this is what actually makes the layered window show the rendered bitmap.
8. Only *then* is the window's position/topmost state (re)asserted and shown via `SetWindowPos`/`ShowWindow` (step 3 in the numbered goals).

**COM initialization: none was required, and I verified this empirically** — the program never calls `CoInitializeEx` anywhere (grepped the final source to confirm), `Win32_System_Com` was a feature in my first draft that I later removed after confirming the build still succeeds without it, and the program runs correctly end to end. This makes sense in retrospect: `D2D1CreateFactory` and `DWriteCreateFactory` are plain DLL export functions (`d2d1.dll`, `dwrite.dll`), not COM class objects instantiated through `CoCreateInstance`, so there's no apartment to initialize. (`Shell_NotifyIconW` for the tray icon also worked with no COM init.) Don't carry a `CoInitializeEx` call into the plan for this particular subsystem — it's dead code here.

**Per-pixel alpha: confirmed working, visually and by measurement.** The rounded panel rendered at alpha ≈0.92 with a smooth anti-aliased 16px corner radius, and Test A's BitBlt (before any affinity call) found 91% of the 480×160 rect matching the exact panel RGB — the missing 9% is exactly the rounded corners + margins outside the rounded rect, which is the expected/correct shape. Text (both the Japanese string `昨日は友達と映画を見に行きました。` and the English line) drew via DirectWrite/Yu Gothic UI with no errors.

## 5. Focus avoidance (goal 1 detail)

Style used: `WS_EX_LAYERED | WS_EX_NOACTIVATE | WS_EX_TOPMOST | WS_EX_TOOLWINDOW | WS_EX_TRANSPARENT`, `WS_POPUP` (no caption/border), created without `WS_VISIBLE`.

**Verification method**: captured `GetForegroundWindow()` immediately before touching the popup at all, then again after each of three different "make it visible" calls, and compared. I deliberately did **not** move the mouse/keyboard myself (per the task's screen constraint) — instead I used whatever real application the user already had focused as the live test subject, which is actually a *better* test than a synthetic one: it's the exact scenario chibipop cares about (does showing the popup steal focus from whatever the user is actually doing).

Results, identical across all 3 runs:
```
foreground BEFORE show:                          HWND(0x21d70ca2)
foreground AFTER ShowWindow(SW_SHOW):             HWND(0x21d70ca2)  unchanged=true
foreground AFTER ShowWindow(SW_SHOWNOACTIVATE):   HWND(0x21d70ca2)  unchanged=true
foreground AFTER SetWindowPos(SWP_NOACTIVATE):    HWND(0x21d70ca2)  unchanged=true
```

Notable: **even plain `ShowWindow(hwnd, SW_SHOW)` did not steal focus here.** I expected `SW_SHOW` to be the negative control (I've seen conflicting claims online about whether `WS_EX_NOACTIVATE` alone is enough to stop `SW_SHOW` from activating), but on this OS build, with `WS_EX_NOACTIVATE` set at window-creation time, `WS_EX_NOACTIVATE` alone was sufficient even against a plain `SW_SHOW`. I still recommend using `SetWindowPos(hwnd, HWND_TOPMOST, x, y, w, h, SWP_NOACTIVATE | SWP_SHOWWINDOW)` as the actual show call in the real app (what the popup ends up using) rather than relying on this — it's the call that simultaneously (a) explicitly declares no-activate intent regardless of ex-style edge cases across OS versions, and (b) sets topmost z-order in the same call, which a real hover-popup needs on every show anyway. Don't treat "`SW_SHOW` also happened to be safe" as a general guarantee for a plan; it's an artifact of `WS_EX_NOACTIVATE` doing the real work here, and that's the flag to keep, not the specific show call.

## 6. Low-level hooks (goal 4 detail)

**Callback signature**: `unsafe extern "system" fn(code: i32, wparam: WPARAM, lparam: LPARAM) -> LRESULT`. This is a plain C-ABI function pointer — `HOOKPROC` in the `windows` crate maps to exactly this shape, and it is passed to `SetWindowsHookExW` as `Some(mouse_hook_proc)`.

**The core gotcha**: this signature cannot be a Rust closure — `extern "system" fn` pointers passed to a C API can't capture any environment. There is no `Box<dyn FnMut>`/trampoline trick available here because Windows itself calls this exact pointer with this exact signature; you don't control the call site. **The only way to get state in or out is through process-global storage.** I used four `static` atomics (`AtomicU32`/`AtomicI32`/`AtomicBool`) written from inside the hook and read from the main loop after pumping messages for a fixed window — e.g. `MSLLHOOKSTRUCT.pt.{x,y}` written to `LAST_MOUSE_X`/`LAST_MOUSE_Y` on every mouse event, and shift state (via `GetAsyncKeyState(VK_SHIFT)`, called from inside the keyboard hook — this is legal/cheap to call from an LL hook, unlike heavier operations) into `SHIFT_DOWN`. For a real popup app, this generalizes to e.g. a `static OnceLock<Mutex<PopupState>>` or a raw `AtomicPtr` holding the HWND, so the hook can decide "should the popup dismiss because the user clicked/scrolled elsewhere" and signal the main thread — but it's still global mutable state either way, unavoidable with this API shape. (I also just called `println!` directly from inside the hook for logging — that sidesteps needing shared state at all for anything that's pure output rather than something the rest of the program needs to react to.)

**Other things confirmed by testing, not just documentation**:
- Both hooks were installed from — and must be unhooked from — the same thread that pumps the message loop. `SetWindowsHookExW(WH_MOUSE_LL, Some(proc), Some(hinstance), 0)` — `dwThreadId = 0` is required for `WH_MOUSE_LL`/`WH_KEYBOARD_LL` specifically (they're always systemwide/global; per-thread installation isn't an option for these two hook IDs the way it is for other `WH_*` values).
- **The hook only actually fires while the installing thread is pumping messages** — `GetMessage`/`PeekMessage` + `DispatchMessage` in a loop. I used a `PeekMessageW`-with-`PM_REMOVE` loop plus a 15ms sleep between drains, running for a fixed 6-second window; this is what let the hook observe real, incidental mouse/keyboard activity from the user's own primary-monitor work without me injecting anything synthetic (I deliberately avoided `SendInput`/moving the OS cursor per the task's constraint — one run of the 6s window happened to catch zero events because the user simply wasn't moving the mouse/typing at that exact moment, which is itself confirmation nothing was being faked: a synthetic-injection test would never show 0 events).
- Real captured events from a run where the user *was* active: mouse coordinates in the primary monitor's coordinate space (e.g. `pt=(2293, 1035)`, `wparam=512` = `WM_MOUSEMOVE`), and real keyboard events (`vk=27` = `VK_ESCAPE`, `wparam` alternating `256`/`257` = `WM_KEYDOWN`/`WM_KEYUP`), confirming both the hook plumbing and the `GetAsyncKeyState`-based shift detection work against genuine system input, not a mock.
- Unhooking: `UnhookWindowsHookEx(mouse_hook)` / `UnhookWindowsHookEx(kb_hook)`, both returned `Ok(())` every run — clean teardown, no leaked hook.
- A real risk I did not personally hit but is documented and worth flagging for the plan: Windows will silently unhook an LL hook if its callback doesn't return promptly (there's a registry-configurable `LowLevelHooksTimeout`, default ~300ms historically). Anything expensive must not happen inside the hook proc itself — push work to the main thread via the global-state pattern above instead of doing it inline.

## 7. Single biggest gotcha a doc-only plan would have missed

**`SetWindowDisplayAffinity(hwnd, WDA_EXCLUDEFROMCAPTURE)` fails with a misleading `ERROR_NOT_ENOUGH_MEMORY` on exactly the kind of window the rest of the spec asks you to build** — a `WS_EX_LAYERED` window painted via `UpdateLayeredWindow` for true per-pixel alpha. Nothing in the `SetWindowDisplayAffinity` or `UpdateLayeredWindow` MSDN pages cross-references this. A plan written from documentation alone would combine goal 1 + goal 2 exactly as specified (layered window, per-pixel alpha, rounded soft panel) and only discover at integration time — probably late, possibly in front of the user — that the single most important requirement (never appear in the app's own screen capture) silently doesn't work, with an error message that actively points a debugging session in the wrong direction ("not enough memory" reads like a resource-exhaustion bug, not an API-compatibility wall). The fix (constant-alpha `SetLayeredWindowAttributes` + `WM_PAINT`, optionally `SetWindowRgn` for a rounded silhouette, giving up true per-pixel AA edges) is a real visual-quality/architecture decision that has to be made *before* writing the rendering code, not patched in after.

Runner-up gotchas, smaller but still real:
- `Error::from_win32()` (the classic windows-rs idiom for "wrap `GetLastError()`") doesn't exist in `windows-result 0.4.1` (used by `windows 0.62.2`) — it's `Error::from_thread()` now. A plan snippet copy-pasted from older windows-rs examples/blog posts will not compile.
- `Win32_Graphics_Dxgi_Common` is very easy to omit from a feature list — it gates exactly one thing used here (`DXGI_FORMAT_B8G8R8A8_UNORM`, needed inside `D2D1_PIXEL_FORMAT`), and omitting it produces a confusing cascade of errors (`D2D1_PIXEL_FORMAT` "not found", then `CreateDCRenderTarget` "method not found") that doesn't obviously point back at a missing Cargo feature.
